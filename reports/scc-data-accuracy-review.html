2. Root causes and corrections

Hardware KPI, summary, status charts, and device register

HwScreen fetched the correct zero inventory from GET /api/v1/hw, but replaced an empty inventory matrix with projectDeviceMatrix sample quantities. Its grand total also used actualTotal || hwTotalDevices(), treating a valid zero as missing data. Status and health calculations used fixed sample proportions regardless of the database, and an empty register was replaced with synthetic device rows.

Fix: summary quantities now come only from persisted inventory. Status calculations use persisted register entries and cannot exceed the corresponding inventory quantity. Units without saved status evidence are explicitly Unknown, not silently assigned Installed, Assigned, In Stock, or Lost. Empty inventory produces zero quantities and zero percentages. Project and department filters use the same matrix. All existing device categories and project choices remain.

Wearables had a separate fallback that injected helmet/watch deployments even when inventory was zero. That fallback has also been removed. Sample installation trends and sample change-history entries are no longer displayed as operational history.

Material Transfers

mergeTransfers returned sample transfers for an empty response and merged additional sample rows into nonempty API results. Two of the sample rows were in transit, explaining the displayed counter of 2. Missing metadata could also be copied from sample transfers with matching IDs.

Fix: only saved API transfer rows are displayed. Empty means zero. Transfer creation previously updated browser state only; it now saves through a capability-checked API before entering the list. Receipt errors are no longer swallowed or presented as successful local confirmations. Receipt permission remains Project PM/receiver, as defined by the existing backend. Device status changes now also save through the API rather than modifying browser-only state.

The existing register Remove button had no saved-delete implementation. It is disabled rather than falsely reporting a deletion; no delete operation was added.

Daily, weekly, and monthly reports

GET /api/v1/reports called _report_packets(), which rebuilt and saved the recent calendar windows even with zero cases and zero weather readings. Historical empty periods became Generated or Awaiting signature. Frontend builders independently created calendar rows when packets were absent, then counted array lengths as report totals.

Fix: calendar windows are now candidates, not completed reports. New packets require real active case data, actual weather measurements, or applicable submitted weekly weather data. Weekly weather aggregates do not invent daily readings. The configured generation cutoffs and HSE/PM signature paths remain functional.

  • The frontend displays API packets only; it never generates missing periods locally.
  • Existing unsigned packets with no source data remain saved and visible as No source data, not completed reports.
  • Scheduled/Compiling periods are excluded from generated-report badges.
  • Generated badges include persisted generated, signed, or historically issued reports; a separate saved-period total makes retention explicit.
  • Saved history outside the recent window, signatures, and historical issue evidence are retained.
  • Empty periods do not trigger compile notifications or allow signing before generation.
  • All catalog projects can participate; reporting is no longer arbitrarily limited to the first four.

Caching, startup, and data sources

No operational hardware/report cache was found in localStorage; its relevant usage is authentication and theme preferences. The mismatches came from rendering fallbacks, browser-only mutations, and request-driven report persistence—not a single stale cache.

The production database resolver requires PostgreSQL and refuses SQLite fallback. Isolated tests use disposable SQLite databases instead. Startup demo seed code is controlled separately from operational case seeding; production defaults disable these fixtures. No seed settings or company/personnel seed code were changed, and no real database was started from the workspace.

5. Verification

Passed: full backend suite (88 tests), frontend suite (20 tests), TypeScript check and Vite production build, and whitespace/error checks. After the final weekly-weather source distinction, the affected accuracy/production-isolation suites passed again (21 tests, including the added regression).
  • Authenticated API tests verify empty hardware, register, transfers, reports, and dashboard KPIs; transfer/status permissions and persistence are exercised.
  • Tests cover actual case-backed generation, weather-only generation including zero-valued measurements, exclusion of missing weather stubs, daily cutoff, weekly HSE signing, monthly dual signatures, and scoped reports.
  • Tests retain all 78 legacy empty packets without counting them as completed, preserve signed/issued archive packets, and verify no empty-period compile notifications.
  • Protected-company-data snapshots remain unchanged across report/hardware reads. Existing SOS Operator direct-close regressions pass.
  • A disposable, fixtures-disabled local preview started cleanly. The sign-in screen rendered without browser errors. No authentication bypass was added.
  • The signed-in UI was not visually verified. Authenticated API behavior and the frontend calculation/build paths were verified separately.
  • Non-blocking warnings remain: the existing Starlette/AnyIO deprecation, mixed static/dynamic imports, and the large JavaScript bundle.

Test invocations used an in-memory/disposable database and process-local development settings, with production bootstrap credentials and SMTP disabled. Existing workspace seed overrides were unset for tests of default configuration behavior; workspace secrets were not changed.

6. Remaining limits and production safety

  • The live app is unchanged. It will keep its old behavior until a separately approved publish. No publish was attempted or suggested as an action.
  • The 78 production packets were not removed or updated during this investigation. With the corrected code in use, unsigned source-less packets are classified as No source data; saved evidence remains retained.
  • Report compilation remains request-driven. A real source-backed period can still be compiled/persisted and notify its existing recipients when reports are read; no production report read was used for verification.
  • Historical installation-event data and detailed hardware change history are not wired to a persisted history feed. Empty history is shown instead of sample claims.
  • Transfer receipt retains its existing status-recording behavior; this work does not introduce a stock-movement reconciliation engine.
  • Read-modify-write JSON state uses the project's existing per-process locking pattern. Cross-instance concurrent edit handling was not redesigned.
  • Production SQL was SELECT-only. No DELETE, TRUNCATE, DROP, UPDATE, reset, migration, account/credential change, company contact/personnel change, or approval-permission change was executed. SOS remains Operator direct-close without Admin approval.
